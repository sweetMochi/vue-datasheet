# 08 — 資料送出給後端的規格不明確

**結論：做一個不猜規格的版本。** 前端做完整驗證，送出後把 `submitPayload` 顯示出來，不打任何 API。
`phase` 進 `submitted`，並提供「回到審核」的出口

---

## 問題不是「沒有端點」，是「不知道規格」

mock 後端只有三支：

```
POST /api/documents                       上傳
GET  /api/documents/{id}/extract          解析（SSE）
GET  /api/health                          健康檢查
```

但題目的情境是「使用者上傳文件 → 後端解析 → 讓使用者確認跟修改」，需求裡也明講
法規必填欄位沒補齊就「**不能就這樣送出去**」。一個真的在跑的審核系統不可能沒有接收端——
**它存在，只是這份題目沒有給我規格**

這個分別很重要，因為它改變了該做什麼：

- 若是「這個系統根本不送出」→ 送出鈕本身就不該存在
- 若是「送出存在但規格未知」→ 要做的是**一個不對規格做假設的版本**，並把所有未知列清楚

採後者

## 不知道的具體有哪些

| 未知            | 影響                                                     |
| --------------- | -------------------------------------------------------- |
| HTTP 方法與路徑 | `POST /api/documents/{id}/fields`？`PUT`？整份還是逐欄？ |
| payload 形狀    | 整份欄位陣列，還是只要 `id` 與 `value`？要不要帶稽核軌跡 |
| 成功回應        | 回 200 空 body，還是回一份正規化後的結果要前端更新畫面   |
| 失敗語意        | 哪些是可重試的、哪些是驗證失敗要逐欄標回畫面             |
| 冪等性          | 重複送出會建立兩筆，還是覆蓋同一筆                       |
| 分次送出        | 上百欄位能不能分次存檔                                   |

---

## 三個選項

| 方案          | 做法                                | 問題                                                                       |
| ------------- | ----------------------------------- | -------------------------------------------------------------------------- |
| **A（採用）** | 驗證 → 顯示 payload，不打 API       | 「已送出」在語意上是假的，要靠文案講清楚                                   |
| B             | 自己訂一個端點 POST 上去，處理 404  | 等於**發明一份規格**。那個 404 還會跟「`document_id` 失效」的 404 撞在一起 |
| C             | 用 Vite middleware 起一個假的接收端 | 同樣是發明規格，而且多花力氣讓「成功」的畫面看起來像真的                   |

**B 與 C 的共同問題是它們都在猜規格**，而猜錯的成本不對稱：猜對沒有加分（反正要重寫），
猜錯則是寫了一整套錯誤處理與狀態轉換，接上真端點時全部作廢

B 還有一個具體的壞處：那個 404 不是真的錯誤，卻會跟
`fetchStreamTransport` 裡「404 = `DOCUMENT_EXPIRED`」的語意撞在一起——
那是換掉 `EventSource` 時費力氣拆開的東西，不該再糊回去

選 A 的理由是**它不發明任何不存在的東西**。真正值得驗的（必填擋住、payload 內容正確、
使用者的值取代後端抽到的值）在 A 裡都驗得到，而且完全不依賴後端

---

## A 的具體契約

**送出前**：`canSubmit` 為真才動作 —— 即 `blockingIssues` 為空且已經有欄位。
送出鈕不灰掉，按下去才說明缺哪幾個並帶使用者過去（見 [README 的介面設計](../README.md#介面設計)）

**送出時**：`markSubmitted()` 只推進 `phase`，不碰網路。`submitPayload` 是 computed，
欄位與草稿都沒被清掉，所以送出後仍然讀得到

**送出後**：`console.table(payload)` 輸出到瀏覽器 console，然後跳出完成對話框，
關掉之後 `reset()` 回到 `idle` 等下一份文件

```ts
store.markSubmitted() // review → submitted（過場，只存在於對話框開著的那幾秒）
console.table(store.submitPayload.value) // 這是這份資料唯一的出口
store.reset() // → idle，清空欄位、草稿、document 與已選檔案
```

### 一句文案上的取捨

原本的契約寫著「不寫『送出成功』這種話」，理由是東西沒有真的送到任何地方。
後來改成**標題寫「送出完成」，內文寫清楚它去了哪裡**：

> 20 個欄位已完成審核，其中 1 個經過修改。
> 後端尚未提供接收端點，所以欄位資料**輸出到瀏覽器 console**（開發者工具 → Console）。

使用者做完一件事需要收到「做完了」的回饋，一個只說「這沒有真的送出」的畫面
會讓人以為自己剛才白做了。標題給回饋、內文給事實，兩件事都成立 ——
真正不能接受的是「已成功送達伺服器」那種謊報

### 為什麼回到 idle 而不是停在「已送出」

審核員的動線是一份接一份。停在終點畫面代表每處理完一份都要多按一次「重來」，
而那個畫面上也沒有任何他還需要的東西 —— 資料已經在 console 裡了

原本為了「submitted 不是死路」而加的 `backToReview()` 在這個流程下沒有呼叫者，
已經移除。留著一個沒有人用、而文件卻描述成刻意設計的函式，比少一個出口更糟

## payload 的形狀

```ts
{
  id, label, group, page, required,
  value,        // 使用者確認後的值，不是後端原本抽到的
  confirmed,    // 使用者按過確認
  edited,       // value !== 後端抽到的值
}
```

**這個形狀是為了給人看而設計的**，因為目前唯一的讀者是螢幕前的人。
`confirmed` 與 `edited` 對真實後端未必有意義，真的接上端點時要依它的 schema 重訂

刻意**沒有**放進去的：`confidence`（後端自己給的，回傳沒有意義）、
後端原本抽到的值（`edited` 已經表示有沒有改，要做稽核再說）

## 這個決定留下的最大空白

上傳與解析的錯誤處理是想過的，光錯誤碼就有五種：

```
DOCUMENT_EXPIRED / BAD_REQUEST / HTTP_ERROR / CONNECTION_LOST / STREAM_TRUNCATED
```

**送出這條路徑一個都沒有**，而且 `ReviewPhase` 也沒有 `submitting`。
不是判斷它不需要，是因為現在沒有任何東西會失敗、也沒有任何等待

這個空白今天看不出來——畫面順、測試全綠——但規格一到就立刻要補：
失敗文案、失敗後 `phase` 停在哪、重複送出的防護、送出中的狀態。
詳見 [REVIEW.md 的第六項](../REVIEW.md#沒把握的地方)

## 測試

4 支，都在 `useReviewStore.test.ts` 的「送出」段：

| 測試                                        | 防住什麼                                        |
| ------------------------------------------- | ----------------------------------------------- |
| 必填補齊後才送得出去，payload 帶使用者的值  | 有人把 payload 改成讀 `fields` 而不是 `drafts`  |
| 送出後 payload 仍讀得到                     | 有人在 `markSubmitted` 裡清掉欄位               |
| 送出後 `reset()` 回到 idle，清得乾淨        | 有人只清欄位忘了清 `document`，下一份會沿用舊的 |
| 缺漏時「跳到第一個」帶的是第一個 id         | 有人改成跳到最後一個或不跳                      |
| 對話框用 `showModal()` 而不是設 `open` 屬性 | 少了焦點鎖定、Esc 關閉、背景 inert              |

## 要問出題方的

1. **payload 的形狀**：整份欄位陣列還是只要 `id` 與值？要不要帶審核者的操作痕跡
   （`confirmed` / `edited`）供稽核？
2. **分次送出**：上百個欄位的文件，審核員可能分兩天處理。要支援嗎？如果要，
   `document_id` 的生命週期就不能是「服務重啟即失效」，前端也需要草稿持久化——
   那會推翻「不裝 `vue-router`、不做持久化」這個決定
3. **送出後可不可以再改**：現在 `backToReview()` 是無條件的。若真實流程送出即鎖定，
   這個出口要拿掉，「已送出」要變成真的終點
